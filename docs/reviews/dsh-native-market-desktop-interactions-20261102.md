# DSH Desktop 插件商城交互复核

## 用户反馈

用户已确认 Store 实际安装成功，但安装后的商城仍无法稳定滚动、搜索，且多项操作不顺畅。当前 Catalog 有 875 条记录（33 条 approved、746 条 blocked、96 条 unlisted），只看审核记录页时会显示 779 条；这不是官网完整发现目录的总量。

## 对照官网完整目录

实时读取 `https://dsh.store/plugins/` 的静态页面元数据后，官网完整目录的 discovery 索引计数为 24,171；其 SHA-256 `fafe139d90916b4ec15548c9d7582f7cb747816a85d15a915a7cda0c334a4f94` 与 GitHub Raw 快照一致。Catalog 索引为 875 条，候选库有 806 条。用官网和 Desktop 共用的 `marketplace/lib/plugin-directory.js` 身份合并逻辑，得到 24,838 条已知记录、945 条与 Catalog 匹配、23,893 条未匹配，覆盖 20 个分类。这个数字随索引快照更新。

完整目录中的审核状态和 Catalog 收录状态分别展示。公开发现、候选、未上架记录仍只能浏览；只有 Catalog 固定记录能提供原有安装入口，最终兼容和安装结果由 DSH Desktop 官方插件管理器判断。

## 根因

- 初始数据加载把 Store Catalog 和 DSH `listBundles()` 安装清单绑在同一个 Promise 上。即使用户只想浏览目录，官方安装清单接口一旦超时或报错，完整目录也不会开始加载。
- 搜索每次按键都会重新遍历完整目录、重建搜索字段，并重新排序两万多条记录；分类选项也在每次渲染时重复构造。
- 列表使用内层固定高度 `overflow:auto`，外层商城面板又有自己的 `overflow:auto`。Desktop 面板滚轮会落在嵌套滚动容器，官网页面则使用单一页面滚动。
- 原测试验证了元素带有 `overflow:auto` 样式，但没有验证单一滚动容器，也没有覆盖安装清单失败时仍可浏览完整目录的情况。

## 修复

- 将 Catalog、完整目录和 DSH 安装清单拆开加载。安装清单暂不可用时仍可浏览、查找全目录；只有依赖本机安装状态的按钮会显示具体原因并禁用，避免把未知状态误当作“未安装”。
- 每份目录快照只生成一次规范化搜索文本，并在排序方式变化时排序；输入时仅过滤索引。分类 ID 也通过 memo 缓存。
- 商城面板成为唯一明确的滚动容器，搜索和筛选栏固定在面板顶部；结果与分页处于同一滚动流，不再使用内层滚动框。
- 页面明确说明 `Catalog 审核记录` 只有商城审核条目；用户要查看官网全量记录时进入 `全部已知插件`。
- 保留官网目录合并、分页和状态语义；Catalog 以外的条目仍没有安装动作，安装结果仍由 DSH 决定。

## 发布边界
