# DSH Desktop fixed-Commit update action

- Trigger: the Desktop Store exposed install, enable, disable, and remove operations, but no update action for an already installed GitHub package. Retrying the same GitHub spec can produce `Already up to date` and no dependency delta, which DSH cannot map to a changed package.
- Root cause: besides the missing update action, `withDesktopTimeout()` accepted an error code but call sites passed timeout durations as that argument. The helper still capped every operation at 12 seconds, and its timeout error code became the number `90000`. A slow GitHub fetch could therefore be reported as a Store failure while DSH continued processing the request.
- Official API contract: the live official latest-three release window is `0.2.1-rc.4`, `0.2.1-rc.5`, and `0.2.2-alpha.2`. In `0.2.2-alpha.2`, `BundleInfo.updatable`, `listVersions()`, and `updateBundle(name, version)` cover registry dependencies; `inspect()` accepts Git specs and `installBundle(spec)` owns Git package/profile operations. Fixed GitHub updates submit the Catalog's new full Commit spec through `installBundle()`. Evidence: [plugin manager types](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-alpha.2/packages/boot/plugin-manager/src/types.ts) and [plugin manager implementation](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-alpha.2/packages/boot/plugin-manager/src/index.ts).
- Change: add an `UPDATE <packageName> <fullCommit>` confirmation for installed bundles whose canonical GitHub repository matches Catalog and whose installed source Commit differs. This includes the Store's own package, which can now update from its Desktop Store page. The action passes only the Catalog's immutable full-Commit GitHub spec to `installBundle()` and preserves the installed enabled state. Timeout handling now takes an explicit duration and a distinct error code: catalog/inspection calls use 12 seconds and install/update operations use 90 seconds, after which the Store reconciles the submitted DSH request without resubmitting it.
- Concurrency and outcome: before submitting, refresh Catalog and Desktop inventory and require the planned source/version/enabled state to remain unchanged. On a DSH failure or uncertain result, reconcile at most once through `waitForInstall()` and `listBundles()`; report success only for the exact target package, version, repository, and full Commit. Otherwise show DSH's refusal/unknown state. Never resubmit automatically.
- Safety boundaries: no custom pnpm command, direct Profile write, Loader/Fiber call, Catalog admission change, or real Profile mutation. Exact package name and target Commit remain part of every confirmation. Official/protected bundles and mismatched repositories remain outside Store management.
- Source verification: focused Desktop harness passed 30/30; `npm run check` passed with `REGISTRY_OK entries=872` and 577/577 tests; `npm pack --dry-run` produced `dsh-safe-plugin-manager@0.9.25`, 1,072 files, 8,511,487 bytes; `node --check src/client.js` and `git diff --check` passed. Typed plan hash verification passed against base `20c086212269a861ef931f120d2fee2d04cecf17` with 10 changed files.
- Publication: source PR and exact-head CI pending. Catalog pin remains at `0.9.24` until a separate fresh Catalog release plan is accepted.
- Acceptance: real DSH Desktop UI/Profile update remains unverified; disposable harness results cannot replace it.
- Rollback: revert the source through an auditable CI-checked PR. Store-triggered package changes are delegated to DSH Desktop's `installBundle()` transaction and require a separate in-app full-Commit confirmation.
